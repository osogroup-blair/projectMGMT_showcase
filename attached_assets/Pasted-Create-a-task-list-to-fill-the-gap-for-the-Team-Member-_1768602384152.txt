Create a task list to fill the gap for the Team Member Auto-Addition During Import

Current Implementation

* Frontend defense: project-new/index.tsx augments roles array with task assignees before submission
* Backend defense: full-create collects all assigneeId from tasks and auto-adds missing as 'member' role
* Dual-layer approach ensures no assignees are lost

Gaps/Limitations

Gap
	Impact
	Priority

No user existence validation - Assignee IDs aren't verified against users table
	Invalid foreign keys
	HIGH

Duplicate role creation risk - Same user could get multiple 'member' roles if in multiple places
	Data duplication
	Medium

No team capacity tracking - Allocations set to 100% regardless of actual availability
	Inaccurate planning
	Low

Missing import-to-system user mapping - External user IDs not resolved to system users
	Broken assignments
	HIGH




Better Approach

* Add validateAndResolveAssignees() function to backend
* Validate user existence before creating team members
* Map external IDs to system users using userMappings
* Return warnings for unresolved assignees

Migration Path

1. Pass userMappings from import context to backend in payload
2. Add user existence validation in full-create
3. Track unresolved assignees in CreationReport.warnings
4. De-duplicate roles by userId before creation



4. Create a task list to fill the gap for the Type Definitions and Data Flow

Current Implementation

* Types defined in multiple locations:
* shared/creation-result-types.ts - payload types
* client/src/lib/import-to-wizard-adapter.ts - imported types
* client/src/pages/project-new/types.ts - wizard types
* No shared validation between frontend/backend

Gaps/Limitations

Gap
	Impact
	Priority

Type duplication - Similar types defined in 3+ places
	Maintenance burden
	Medium

No runtime validation - TypeScript types don't protect at runtime
	Silent failures
	HIGH

Inconsistent optional fields - Some types use ?, others use or null
	Confusing API contract
	Medium

Missing discriminated unions - Error states not type-safe
	Poor error handling
	Medium




Better Approach

* Create shared/import-types.ts as single source of truth
* Use Zod schemas for both type inference and runtime validation
* Export both types and schemas from shared location
* Use same schema for frontend and backend validation

Migration Path

1. Create shared/import-types.ts with Zod schemas
2. Export both types and schemas from shared
3. Use schemas for validation in both frontend adapter and backend endpoint
4. Remove duplicate type definitions
