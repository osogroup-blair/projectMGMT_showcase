Create a plan and implementation to support **subtasks, task dependencies, and task types** within projects and sprints.

This feature must work across project tasks, sprint boards, and task views without breaking existing workflows. Task Types must be designed so they can be reliably used for filtering and reporting later.

GOALS
- Allow tasks to be broken down into subtasks.
- Allow tasks to depend on other tasks.
- Introduce Task Types as a first-class attribute.
- Ensure Task Types are globally defined but configurable per project.
- Make dependencies and task types visible and usable without adding complexity.

---

TASK TYPES (NEW — MUST IMPLEMENT)

CONCEPT
- Every task has a Task Type.
- Task Types are used for:
  - Filtering (boards, lists, dashboards)
  - Grouping and reporting
  - Templates and automation later

SCOPE & CONFIGURATION
- Task Types are defined at two levels:
  1) **Global App Defaults**
     - Managed in admin/app settings
     - Example: Feature, Bug, Chore, Research, Spike
  2) **Project-Level Overrides**
     - Managed in Project Settings
     - Projects can:
       - Enable/disable global task types
       - Add project-specific task types
       - Rename labels (optional, if supported)

RULES
- Every task must have a Task Type.
- If not explicitly set, a default Task Type is applied automatically.
- Subtasks inherit the parent task’s Task Type by default (but can be changed if allowed).

UI
- Task Type selector in:
  - Task creation
  - Task detail view
- Task Type shown as a small badge on task rows/cards.
- Task Type filter available in:
  - Project task overview
  - Sprint boards
  - Run tab (future-safe)

---

SUBTASKS

REQUIREMENTS
- A task can have zero or more subtasks.
- Subtasks are lightweight tasks with:
  - title
  - status
  - taskTypeId
  - assignee (optional)
  - due date (optional)
- Subtasks inherit project, stage, sprint, and Task Type from the parent by default.

BEHAVIOR
- Subtasks appear:
  - In the parent task detail view
  - As a collapsible section in task lists (optional)
- Parent task progress is derived from subtask completion:
  - Show completion count (e.g., 3/5)
  - Optional: auto-complete parent when all subtasks are done
- Subtasks are not shown as separate cards on boards by default.

---

TASK DEPENDENCIES

REQUIREMENTS
- A task can depend on one or more other tasks.
- Supported dependency type (v1):
  - Finish-to-start (this task is blocked until dependency is done)
- Dependencies are limited to tasks within the same project.

BEHAVIOR
- If dependencies are incomplete:
  - Task is automatically marked Blocked
  - Blocked reason references the dependency task(s)
- When all dependencies are completed:
  - Task is automatically unblocked
- Circular dependencies must be prevented.

UI
- In task detail:
  - “Blocked by” selector (choose tasks)
  - “Blocking” list (read-only)
- Dependency indicator on task rows/cards.
- Clicking dependency opens the referenced task.

---

SPRINT & BOARD INTEGRATION

REQUIREMENTS
- Task Type is available as a filter on:
  - Sprint boards
  - Sprint Run tab
  - Project task overview
- Subtasks do not appear as top-level board cards by default.
- Tasks blocked by dependencies show a blocked indicator.
- Dragging a blocked task to “In Progress” should:
  - Warn the user
  - Optionally allow override with confirmation

---

DATA MODEL (HIGH LEVEL)

Task
- id
- title
- status
- taskTypeId
- parentTaskId (nullable)
- assigneeId
- dueDate
- projectId
- stageId
- sprintId

TaskType
- id
- name
- scope: GLOBAL | PROJECT
- projectId (nullable)
- isActive

TaskDependency
- id
- taskId (dependent)
- dependsOnTaskId

RULES
- parentTaskId and TaskDependency graphs must not contain cycles.
- Deleting a task with subtasks requires confirmation or cascading behavior.
- Deleting a Task Type requires reassignment to a fallback type.

---

API REQUIREMENTS (SUGGESTED)

- GET /api/task-types
- POST /api/projects/:projectId/task-types
- POST /api/tasks/:id/subtasks
- POST /api/tasks/:id/dependencies
- DELETE /api/task-dependencies/:id
- PATCH /api/tasks/:id (status, assignee, taskTypeId, etc.)

---

ACCEPTANCE CRITERIA

TASK TYPES
- Global Task Types can be defined and reused.
- Projects can customize available Task Types.
- Every task always has a valid Task Type.
- Task Type filtering works across project and sprint views.

SUBTASKS
- Subtasks can be created, edited, reordered, and completed.
- Parent task progress reflects subtask completion.
- Subtasks do not clutter boards.

DEPENDENCIES
- Dependencies can be created and removed.
- Blocked tasks are clearly indicated.
- Completing dependencies automatically unblocks tasks.
- Circular dependencies are prevented.

UX
- Adding subtasks, dependencies, or task types requires minimal interaction.
- Indicators are clear and non-intrusive.
- No regressions in existing task, sprint, or board behavior.

CONSTRAINTS
- No Gantt charts in v1.
- No cross-project dependencies.
- Task Types must be future-safe for filtering and reporting.
- Keep UI lightweight and performant.

Start by proposing the data model changes and validation rules before implementing UI.
