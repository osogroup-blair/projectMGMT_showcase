# App-Gen Prompt: Reusable “Tasks by Person” UI Component Set (Design → Implement)

You are designing and implementing a **reusable UI component set** for a project management application.  
Focus strictly on **capabilities, functionality, and usability**.  
Do **not** reference any specific technologies, frameworks, or tech stacks.

---

## Goal
Design and implement a **“Tasks by Person” component** that can be reused across multiple areas of the application (Project Overview, Dashboards, Sprint pages, Milestones, Deliverables, Team views).

The component must be **configuration-driven**, meaning each page can control:
- Which people are shown
- Which actions are allowed
- Which scopes are available
- Whether the user can edit or only view data

The component must support:
- Viewing all tasks assigned to a person across the entire project
- Filtering tasks by **Sprint, Milestone, Deliverable, or Unscoped**
- Switching between list and card views
- Inline task updates (when permitted)
- Clear navigation back to the task’s source context
- A **“Just My Tasks”** mode for focused personal work

---

## Output Requirements
Produce:
1. **UX and interaction design specification**
2. **Component capability and configuration contract**
3. **Data and behavior expectations** (inputs, outputs, updates)
4. **Implementation behavior plan** (what the component must do, not how)
5. **Acceptance criteria** using clear Given / When / Then language
6. **Edge case and usability considerations**

---

## Feature Definition

### Component Set Name
**Tasks by Person**

Includes:
- A wrapper panel that manages people and filters
- A per-person task card
- Supporting controls and views

---

## Core Concept
A **Person Workload Lens** that shows:
- Who the person is
- How much work they have
- Where that work lives in the project
- What actions can be taken without leaving context

The component must scale from:
- A single user view (“Just My Tasks”)
- To a full team overview (“All People”)

---

## “Just My Tasks” Toggle (Required)

### Purpose
Allow users to instantly focus on **their own work** without navigating away or changing pages.

### User Experience
- A clearly labeled toggle:  
  **All People | Just My Tasks**
- When enabled:
  - Only the current user’s tasks are shown
  - Only one person card is rendered
- When disabled:
  - All relevant people cards are shown
- The toggle should:
  - Preserve filters and view selections
  - Update metrics and counts correctly
  - Be optionally hidden by the embedding page

---

## Collapsed Card State (Default)

Each person is represented by a **long horizontal card**.

### Contents
- Person identity:
  - Avatar
  - Name
  - Optional role or team
- Project-level metrics:
  - Total open tasks
  - Overdue tasks
  - Tasks due soon or in the current sprint
  - Blocked tasks
  - Completion percentage
- Scope indicators:
  - Visual signals showing whether the person has tasks in:
    - Sprints
    - Milestones
    - Deliverables
    - Unscoped work
- Overall status:
  - On Track
  - At Risk
  - Off Track
- Expand / collapse control

The collapsed state must allow users to quickly scan workload health without expanding.

---

## Expanded Card State (Task Explorer)

When expanded, the card becomes a **focused task workspace** for that person.

### Top Controls
- **Scope filter selector**
  - All Tasks
  - Sprints (grouped)
  - Milestones (grouped)
  - Deliverables (grouped)
  - Unscoped
- **View toggle**
  - List view (default)
  - Compact card view
- **Quick filters**
  - Status
  - Priority
  - Due date ranges (Overdue, This Week, Upcoming)
  - Blocked only

---

## Task Display Requirements

Each task must show:
- Task title (clickable)
- Current status
- Due date
- Priority indicator
- Blocked indicator
- Scope context:
  - Deliverable → Milestone → Sprint (when applicable)
- A quick actions menu (if allowed)

### Navigation Rules
- Selecting a task must navigate the user to the **correct context**:
  - Sprint view if the task is in a sprint
  - Milestone view if not in a sprint
  - Deliverable view if not in a milestone
  - Task detail view if unscoped

---

## Configuration & Reusability (Critical)

The component must **never assume context**.

### Configuration Capabilities
The embedding page must be able to control:
- Which people are shown
- Whether “Just My Tasks” is available
- Default expanded or collapsed state
- Allowed scopes
- Allowed actions (view-only vs editable)
- Current contextual scope (if any)
- Navigation behavior

This ensures the same component can be used everywhere without modification.

---

## Data & Behavior Expectations

### Inputs the Component Expects
- Current user identity
- Project membership list (when showing all people)
- Per-person task summaries
- Per-person task lists
- Available scopes (sprints, milestones, deliverables)

### Behaviors the Component Must Support
- Refreshing data when filters or toggles change
- Updating metrics when tasks change
- Inline updates when permitted
- Graceful handling of stale or conflicting updates
- Immediate visual feedback for changes

---

## States to Design and Support

### Loading
- Skeleton states for cards and task lists

### Empty
- No tasks for a person
- No tasks matching current filters
- No people available to display

### Error
- Unable to load people
- Unable to load tasks
- Unable to apply updates

### Permission-Based
- Read-only views with disabled actions and clear affordances

### Performance
- Large numbers of people
- Large numbers of tasks
- Progressive rendering or lazy expansion as needed

---

## Accessibility & Usability
- Full keyboard navigation
- Clear focus indicators
- Expand/collapse and toggle controls accessible without a mouse
- Clear labels and tooltips for all icons and metrics

---

## Acceptance Criteria (Examples)

- **Given** the panel is in “All People” mode  
  **When** the user enables “Just My Tasks”  
  **Then** only the current user’s task card is displayed

- **Given** a person has tasks across multiple scopes  
  **When** the card is expanded  
  **Then** tasks are grouped and filterable by scope

- **Given** inline editing is disabled  
  **When** the user interacts with task fields  
  **Then** fields are read-only and show a disabled state with explanation

- **Given** a task is updated elsewhere  
  **When** the user attempts to modify it  
  **Then** the component refreshes and communicates the conflict clearly

---

## Edge Cases to Address
- Current user is not part of the project
- Tasks exist without any scope
- Permissions differ between pages
- Users switch between “Just My Tasks” and “All People” rapidly
- Very large projects with many people and tasks
