# Prompt — Build Auth-First User Profile + Identity Linking (Atomic Modular, schema-driven)

You are an Expert AI Architect working in a strictly decoupled Atomic Modular system.

We need to create a **User Profile** that can **tie multiple identities together** across systems (providers/workspaces), now that authentication exists. Use the attached template schema as the canonical starting point and do not invent incompatible shapes. The template includes:
- `Users[]` with fields like `id`, `name`, `role`, `email`, `status`, `avatar`
- `identities[]` with `identityId`, `system{systemId, systemType, systemName, workspaceId}`, external identifiers, `auth{authType, provider, scopes, tokenRef, tokenExpiresAt}`, roles/permissions, profile info, sync info, and metadata. :contentReference[oaicite:1]{index=1}

## Non-negotiables
- No file > 700 LOC; target ~200 LOC/module.
- Follow Atomic Modular layering:
  - `/apps` UI routes only
  - `/services` business operations (atomic unit = Operation)
  - `/data` contracts/schemas/types
  - `/integrations` external providers (anti-corruption)
  - `/packages` plug-and-play (activation/deactivation docs)
  - `/components` shared dumb UI
- Context Rule: read + update relevant `SUMMARY.md` files before/after changes.

## Deliverables

### 1) Data model & contracts (in `/data`)
Using the provided template, define:
- `User` (the canonical profile)
- `Identity` (a link to an external system user)
- `SystemRef` (system/workspace identity scope)
- enums: `status`, `identityType`, `systemType`, `authType`, `syncStatus`
- validation constraints:
  - `User.id` is stable canonical id
  - `Identity.identityId` stable internal id
  - Identity uniqueness keys:
    - (`system.systemId` + `externalUserId`) OR (`system.workspaceId` + `externalUserId`) depending on provider rules
  - one identity can belong to only one user
  - one user can have many identities
  - support “source of truth” and syncing fields (from template)
- define a minimal **public profile** projection (no tokens / tokenRef leakage)

Also propose any **schema improvements** that preserve compatibility (e.g., add `primaryIdentityId`, `primaryEmail`, `userHandle`, `mergedIntoUserId`, `identityLinkState`, etc.) but do not remove fields from the template.

### 2) Service operations (in `/services/user-management`)
Design and implement atomic operations that enable identity linking:

**Core operations**
- `getCurrentUserProfile(authContext)`
- `getUserProfile(userId, authContext)`
- `updateUserProfile(userId, patch, authContext)` (profile-only; no identity linking here)

**Identity linking operations**
- `linkIdentityToUser(userId, identityInput, authContext)`
- `unlinkIdentityFromUser(userId, identityId, authContext)` (with safeguards)
- `resolveOrCreateUserFromAuth(authPayload)`:
  - given auth provider + external identifiers (email/sub/provider user id), find matching Identity
  - if found, return canonical User profile
  - if not found, create User + Identity (or create Identity and attach to existing User based on rules)
- `mergeUsers(sourceUserId, targetUserId, authContext)`:
  - move identities, reconcile conflicts, preserve audit trail
  - mark source as merged (soft state) rather than deleting

**Policy requirements**
- Enforce org/tenant scope if relevant (via `system.workspaceId` or a separate orgId)
- RBAC: only admins can link/unlink/merge users (unless self-service rules are explicitly specified)
- Never expose `tokenRef` to clients; it stays server-side only.

### 3) App routes/UI (in `/apps/...`)
Create user-aware UI flows:
- Profile view/edit (user)
- Admin user lookup
- Identity list per user
- Link new identity flow:
  - choose provider/system/workspace
  - enter external identifiers or complete provider OAuth
  - confirm link (show conflict warnings)
- Unlink identity flow (with prevention if it is the last login identity)

All routes must be user-aware (auth required) and call services only.

### 4) Integrations (in `/integrations/{provider}`)
If identities come from OAuth / external directory providers:
- Implement anti-corruption adapter(s) that map provider claims → template fields:
  - external id / username / email
  - system/workspace mapping
  - scopes, tokenRef handling, token expiry
- Ensure `/services` only sees domain contracts from `/data`, never raw provider shapes.

### 5) Storage + constraints
Define storage strategy and constraints:
- indexes for identity uniqueness
- transaction strategy for link/unlink/merge
- audit metadata population (`createdAt/updatedAt/createdBy/updatedBy`)
- sync metadata updates (`lastSyncedAt`, `syncStatus`, `lastError`)

### 6) Output format required
Return:
1. **Proposed contract types** (User, Identity, SystemRef, enums) aligned to the template
2. **Linking & merge rules** (deterministic match strategy + conflict resolution)
3. **Service operations list** with inputs/outputs and authorization rules
4. **Route list** for Profile + Admin user management
5. **Refactor plan** broken into ~200 LOC modules
6. **Which SUMMARY.md files you read and how you updated them**

Now perform the design and provide the plan + recommended schema adjustments.
