You are a senior full-stack engineer working in an existing shared-component architecture. Create a **detailed, execution-ready task list** to implement a **shared “Task Inspector” Right Sidebar** component that slides in/out and allows lightweight editing of a task.

## Goal
Build a reusable right-side drawer (sidebar) that:
- Opens from the right and can **collapse/expand** and supports **dynamic width** (preset widths + drag resize).
- Provides a **simple “review & edit”** surface for a task (not the full task detail experience).
- Lets users **map the task to time-boxed objects** (e.g., Sprint, Epic, Deliverable/Stage, Milestone—use the app’s actual hierarchy) and **navigate** to those linked objects.
- Is **context-aware**: when opened from different pages, it should infer what to show by default (e.g., if opened from a Sprint view, default the “Timebox” tab/section and highlight the Sprint association).
- Is **tabbed** with at least: **Overview**, **Comments**, **Subtasks**.
- Allows **Subtasks** to be explored inside the same sidebar with **independent back navigation** (a mini navigation stack inside the drawer), without losing the parent task context.
- Includes a clear CTA to open the **full Task Detail Page** for advanced functionality.

## Constraints / Non-goals
- Keep the MVP minimal: only essential fields and navigation (no massive forms, no complex workflows).
- Must match the existing codebase patterns: routing, state management, styling, component conventions, and API/data fetching.
- Must be implemented as a shared component that can be invoked from multiple pages consistently.

## Deliverable format
Return a task list that is broken down into:
1) **Discovery / Codebase Alignment**
2) **Component Architecture**
3) **State & Data Model**
4) **UI/UX Tasks**
5) **Navigation & Context Awareness**
6) **Subtask Exploration (Nested Navigation)**
7) **Integrations (API/hooks/services)**
8) **Testing (unit/integration/e2e)**
9) **Performance & Accessibility**
10) **Rollout / Feature Flag / Telemetry**
11) **Documentation**

## Task list requirements
For each task, include:
- A short **task title**
- A **description** with implementation notes
- **Acceptance Criteria** (clear, testable bullets)
- Any **dependencies** (what must be done first)
- If relevant, **file/module touchpoints** to look for (e.g., “shared/components”, “routes”, “task hooks”, “comment service” — adapt to repo reality)

## Sidebar MVP scope (include these fields/features)
- Header: Task title + status + quick link “Open full details”
- Overview: editable fields limited to:
  - Status
  - Assignee(s)
  - Due date
  - Priority (if exists)
  - Timebox mapping (Sprint/Epic/etc.)
- Comments tab:
  - List + add comment
  - Mention support if already in codebase; otherwise explicitly call it out as “out of scope”
- Subtasks tab:
  - List subtasks
  - Click subtask opens that subtask in the same sidebar with back button
  - “Create subtask” only if codebase already supports it; otherwise keep out of scope
- Footer: Close, Expand/Collapse control, width preset selector (e.g., S/M/L) and drag resize (optional but preferred)

## Engineering expectations
- Identify the minimal API/data requirements and how to reuse existing hooks/services.
- Provide a strategy for avoiding unnecessary refetch (cache/optimistic updates if already used).
- Include accessibility requirements: focus trap, ESC to close, ARIA roles, keyboard navigation.
- Ensure the component supports deep-linking if applicable (e.g., query param `?taskId=`) OR explicitly document why not.

- Be specific and concrete, not generic.
