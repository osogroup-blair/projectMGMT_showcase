App Gen Prompt: Sprint Functionality Implementation Plan

You are a senior product + engineering lead. Create a detailed, actionable plan to add Sprint functionality to an existing Project Management application.

Context

The app currently has these core concepts:

Projects contain Deliverables, Epics, Tasks, Milestones, and ProjectStages

ProjectStages represent workflow (e.g., Backlog → In Progress → Done)

Milestones represent outcomes and can link to tasks directly and via a join entity MilestoneTaskLinks

Tasks already support assignment to Users, Comments, Attachments, and History.

We are adding Sprints as timeboxes, separate from workflow stages.

Data Model Requirements

Add the following entities and relationships:

New Entities

Sprints

id, project_id, owner_user_id, name, start_date, end_date, status (planned|active|closed), goal

SprintMembers (optional but recommended)

id, sprint_id, user_id, capacity_hours, capacity_points

SprintScopeEvents (optional but recommended)

id, sprint_id, task_id, user_id, event_type (added|removed|moved_in|moved_out|reestimated), occurred_at, note

Relationships

Projects 1—* Sprints

Sprints 1—* Tasks (add nullable tasks.sprint_id)

Keep tasks.stage_id for workflow stages (do not repurpose stages as sprints)

Keep milestone relationships unchanged.

What to Produce

Generate a plan that includes:

Product scope

Sprint lifecycle: planned → active → closed

Sprint planning features: add/remove tasks to sprint, move tasks between sprints, backlog handling

Sprint execution: daily task movement across stages while remaining in sprint

Sprint close behaviors: what happens to incomplete tasks; reporting impact

Database changes

SQL schema changes (DDL) for the new tables + indexes

Update Tasks schema to include sprint_id and recommended indexes

Data migration strategy for existing projects/tasks (default backlog = null sprint)

API / backend

Endpoints (or service methods) for:

create/update/delete sprint

start sprint / close sprint

assign/unassign task to sprint

bulk move tasks between sprints

sprint capacity endpoints (if SprintMembers included)

sprint scope event logging rules (when to create events)

Validation rules:

task must belong to same project as sprint

only one active sprint assignment per task

cannot change dates/status illegally (e.g., closed sprint edits)

Authorization expectations using RoleAssignments/ProjectRoles (assume roles exist)

UI plan

New screens/components:

Sprint List (per project)

Sprint Detail (goal, dates, members/capacity, scope tasks)

Sprint Planner (Backlog ↔ Sprint)

Sprint Board (filter board by sprint)

Sprint Close modal (carry over options)

UX flows:

Create sprint → add tasks → start sprint

Mid-sprint scope change

Close sprint + carry over

Suggested UI states and empty states

Reporting & analytics

Metrics:

committed vs completed tasks

velocity (points or task count)

scope change count (from SprintScopeEvents)

Simple burndown logic (high-level)

Implementation phases

Phase 1: minimal viable sprint (Sprints + tasks.sprint_id + planner)

Phase 2: SprintMembers capacity + sprint close workflow

Phase 3: SprintScopeEvents + analytics/burndown

Testing plan

Unit tests for validation rules

Integration tests for sprint start/close flows

UI tests for drag/drop or bulk assignment

Edge cases (tasks in closed sprint, changing project, etc.)

Output Format

Return:

A structured plan with headings

A checklist of tasks grouped by phase

Example payloads for key API calls

Schema DDL in a code block

Important constraints:

Do not model sprints as stages.

Ensure tasks can have both a Stage (workflow) and Sprint (timebox) simultaneously.

Keep it realistic and implementation-ready.

Prefer clear defaults and incremental delivery over “boil the ocean.”
