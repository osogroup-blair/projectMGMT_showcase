You are implementing the **Sprint “Run” Tab**. This is the ACTIVE sprint execution surface that combines:
1) **Flow Mode** (move tasks through statuses on a board)
2) **Pulse Mode** (async standups + sprint awareness)

This is NOT a generic task board. It must be sprint-scoped and optimized for daily execution + alignment without meetings.

ROUTE & SCOPE
- Route: /projects/:projectId/sprints/:sprintId/run (or a “Run” tab within sprint detail)
- Scope: ONE sprint only (all data and actions sprint-scoped)

PRIMARY JOB
“Help the team move work forward AND stay aligned day-to-day asynchronously.”

A sprint lead must be able to answer in < 15 seconds:
- “Is the sprint moving forward today?”
- “Who is blocked and why?”
- “What changed since yesterday?”

---

CORE PRINCIPLES (MUST FOLLOW)
1) Board is primary: moving tasks through statuses must be fast.
2) Pulse is always visible: async standup should be built-in, not a separate feature.
3) No double entry: board activity should auto-suggest content for updates.
4) Structured updates > chat: async standup is prompt-based, skimmable.
5) Frictionless: posting an update should take < 60 seconds.

---

PAGE LAYOUT (RECOMMENDED)
Two-pane layout:
- Left (≈65%): FLOW BOARD
- Right (≈35%): PULSE (ASYNC STANDUP + SIGNALS)

Include a sticky top header.

---

A) SPRINT HEADER (STICKY)
Show:
- Sprint name
- Date range
- Sprint goal (inline editable)
- Health chip: On Track / At Risk
- Counts (clickable filters):
  - Total tasks
  - Done
  - In Progress
  - Blocked
  - Overdue

Behavior:
- Clicking a count applies a filter to the board (and optionally Pulse feed).

---

B) FLOW MODE — ACTIVE BOARD (LEFT PANE)

1) Columns = Sprint Statuses
- Use existing status model if present; else default:
  - To Do, In Progress, Review, Done, Blocked
- Must support drag-and-drop task movement between columns.

2) Task Card (Minimal but high-signal)
Each card shows:
- Title
- Assignee avatar/name
- Due date (optional) with urgency indicator
- Flags: Blocked, Overdue
- Optional badges: Epic, Stage, Milestone

3) Inline Actions (from card or quick menu)
- Change status (via drag or menu)
- Assign/reassign user
- Mark blocked/unblocked
- Open details (side panel preferred)

4) Guardrails (to improve async signal quality)
- Moving to “Blocked” MUST prompt for a blocker reason (short text)
- Moving to “Done” SHOULD optionally prompt for a quick completion note (“What changed?”) (make it skippable)

5) Board Filters (sprint-scoped)
- Status (multi)
- Assignee
- Blocked only toggle
- Overdue only toggle
- Search

Rules:
- Filters are instant and do not reload the whole page.
- Persist filters per user per sprint (optional v1.1).

---

C) PULSE MODE — ASYNC STANDUP + SPRINT AWARENESS (RIGHT PANE)

Pulse has two stacked sections:
1) “Sprint Signals” (small, at top)
2) “Async Standup Feed” (main)

---

C1) Sprint Signals (Derived)
Show small signal cards:
- Blockers: # (click filters board to blocked)
- Overdue: #
- Stale tasks: # tasks not moved in ≥ N days (default N=3)
- Optional v1.1: “Risk trend” indicator

These are rule-based heuristics, not heavy analytics.

---

C2) Async Standup (Per user per day per sprint)
Users can post ONE update per day (can edit same day).

Update prompts (structured):
- “Since last update, what did you do?”
- “What will you do next?”
- “Any blockers?”

Each prompt is optional but encouraged.

Update includes:
- userId
- sprintId
- date (local day)
- text fields above
- referencedTaskIds[] (auto + manual selection)
- blockerReason (if blocked)

Feed Behavior:
- Show updates grouped by day (Today, Yesterday, Earlier)
- Most recent day at top
- Within day: most recent first

---

D) NO DOUBLE ENTRY — AUTO-SUGGESTIONS (CRITICAL)

When a user opens the “Post Update” panel, pre-fill suggestions based on activity since their last update:
- Tasks moved to Done → suggested under “did”
- Tasks moved to In Progress/Review → suggested under “next”
- Tasks marked Blocked → suggested under “blockers” with blocker reason
- Optionally include “tasks touched” based on updatedAt/activity log

Users can:
- Accept suggestions with one click
- Remove items
- Add additional context

Posting an update should be possible in < 60 seconds.

---

E) REQUIRED DATA & MODELS

Minimum data required:
- Sprint (id, name, start, end, goal)
- Sprint tasks with:
  - id, title, status, assigneeId, dueDate
  - blocked flag + blocker reason (or status=Blocked)
  - updatedAt or activity log
- Users (id, name, avatar)
- Async standup updates:
  - sprintId, userId, date, did, next, blockers, referencedTaskIds

If no activity system exists, use updatedAt and status changes as “activity”.

---

F) API REQUIREMENTS (SUGGESTED)

1) Sprint Run data
GET /api/projects/:projectId/sprints/:sprintId/run
returns:
- sprint summary
- statuses/columns
- tasks (with enough fields for board)
- signals summary
- recent pulse updates

2) Update task status/assignment/blockers (existing endpoints OK)
- Must support fast status update from drag-and-drop
- If status becomes Blocked, require blocker reason

3) Pulse endpoints
- GET /api/sprints/:sprintId/pulse?from=... (optional)
- POST /api/sprints/:sprintId/pulse (create/update today’s entry)
- GET /api/sprints/:sprintId/pulse/suggestions?userId=... (optional)
  returns suggested tasks + text blocks derived from activity

4) Notifications (DO NOT SPAM)
- No notification per status move.
- Optional: daily digest summary (future).

---

G) ACCEPTANCE CRITERIA (TESTABLE)

FLOW BOARD
- Dragging a task moves it to a new status and persists to backend.
- Marking Blocked requires a blocker reason.
- Filters work instantly and correctly.
- Task details open without leaving the Run tab (side panel preferred).

PULSE
- User can submit an update for today (one per day per sprint).
- Updates display grouped by day and are skimmable.
- Updates link to referenced tasks.
- Blocker badge visible if blockers present.

AUTO-SUGGESTIONS
- When opening update composer, suggestions appear based on recent activity.
- User can accept suggestions quickly.
- Posting takes < 60 seconds.

SIGNALS
- Blockers count matches actual blocked tasks.
- Overdue count matches due dates and status.
- Stale tasks rule works (no movement in ≥3 days).

PERFORMANCE & UX
- Initial load renders quickly; do not render hundreds of tasks without virtualization/pagination.
- No console errors.
- Run tab works on typical screen sizes.

---

H) NON-GOALS (DO NOT BUILD IN v1)
- Chat room / threaded discussions in Pulse
- Complex burndown charts or forecasting
- Cross-sprint or cross-project analytics
- Mandatory standup enforcement (no hard blocks if user skips)
