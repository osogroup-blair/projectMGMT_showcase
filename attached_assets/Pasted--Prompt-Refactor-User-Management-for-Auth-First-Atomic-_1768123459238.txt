# Prompt — Refactor User Management for Auth-First, Atomic Modular Architecture (700 LOC max / ~200 target)

You are an **Expert AI Architect** maintaining a strictly decoupled **Atomic Modular system**.  
We have **recently added authentication**. Your job is to **refactor “User Management” end-to-end** so it is fully **auth-first**, **user-aware**, and aligned to the architecture manifest.

## Non-Negotiables
- **No file > 700 lines**. Target **~200 lines** per file whenever practical.
- **Context Rule:** `SUMMARY.md` files are the system’s **Living Memory**.
  - Before changes: read root `SUMMARY.md` + all relevant folder-level `SUMMARY.md`.
  - After changes: update all impacted `SUMMARY.md` to reflect the **actual** structure, dependencies, and consumers.
- Strict layering:
  - `/apps` (Delivery) — routes/pages UI only, atomic unit = `SubTab`
  - `/services` (Logic) — domain ops, atomic unit = `Operation`
  - `/data` (Contract) — types/schemas, atomic unit = `Type/Entity`
  - `/integrations` (Bridge) — external adapters, atomic unit = `Provider`
  - `/packages` (Foundation) — plug-and-play features, must have `ACTIVATION.md` + `DEACTIVATION.md`
  - `/components` (UI Library) — shared UI atoms/patterns

## Goal
Refactor the **User Management** feature so that:
1. Every User Management route is **User Aware**
2. All data access is **scoped** by authenticated identity (user/org/tenant)
3. RBAC/permissions are enforced consistently
4. The domain logic lives in `/services` (not in pages/components)
5. Data contracts live in `/data`, and integrations (if any) are isolated in `/integrations`
6. The feature becomes modular, testable, and maintainable under the file-size constraints

## What to Do (Required Steps)

### 1) Discover & Map Current User Management
- Identify all User Management entry points:
  - UI routes/pages in `/apps` (list them)
  - related UI components in `/components`
  - related services in `/services`
  - related types/schemas in `/data`
  - related adapters in `/integrations`
  - related packages in `/packages`
- Output a “current state map”:
  - What the main user flows are (list)
  - Where auth checks happen today (if any)
  - Where user identity is sourced from (session/jwt/middleware/server helper)
  - Where user/org scoping happens today (if any)

### 2) Define the Auth-First User Management Domain
Create (or refine) the domain contracts and operations:

**Contracts (`/data`)**
- `User` entity types (public vs internal shape)
- `Role`, `Permission`, `Membership` (if applicable)
- Request/response schemas for operations
- Auditing/event shapes (if applicable)

**Operations (`/services/user-management`)**
Each operation should be atomic and single-responsibility. Examples:
- `getCurrentUser`
- `listUsers` (scoped)
- `getUserById` (scoped)
- `inviteUser` (scoped + permissions)
- `updateUserProfile` (scoped)
- `updateUserRole` (scoped + permissions)
- `deactivateUser` (scoped + permissions)

For each operation:
- Define input/output types (from `/data`)
- Define required auth context (userId, orgId/tenantId)
- Define permission checks (RBAC/ABAC)
- Define error semantics (unauthorized, forbidden, not found, conflict)

### 3) Enforce “User Aware” Pages for User Management
Every User Management page/route must:
- Require authentication before rendering
- Use a consistent method to obtain auth context
- Fetch only scoped data through services (no direct db/provider calls in UI)
- Enforce permissions consistently (deny by default)

Deliver:
- A table of routes/pages and their required permissions
- A consistent pattern: layout guard / middleware / server loader (depending on stack)
- Identify any public routes (if any) and justify them explicitly

### 4) Remove Layer Violations & Split Oversized Files
- Find and refactor any files in User Management that:
  - combine UI + business rules + data access
  - exceed 700 LOC (must fix)
  - exceed ~200 LOC (should be decomposed)
- Produce a concrete refactor breakdown:
  - new file names, their responsibilities, and which layer they live in
  - dependency direction (apps → services → data; apps → components; services → integrations; etc.)

### 5) Integrations & Anti-Corruption (If User Data Touches External Systems)
If User Management depends on external auth/identity providers (or other systems):
- Keep provider-specific shapes isolated in `/integrations/{provider}`
- Provide mapping layers so `/services` only sees domain types from `/data`
- Document the adapter contracts

### 6) Implementation Plan + Verification
Provide a phased plan:

**Phase 0 — Safety**
- Identify test gaps
- Add/confirm “golden path” tests (login → user mgmt → role change)
- Add permission tests (unauthenticated, authenticated/no-permission, permitted)

**Phase 1 — Auth Context Normalization**
- Centralize how auth context is obtained (server helper / middleware / hook)
- Ensure every user mgmt entry point uses it

**Phase 2 — Service Extraction**
- Move business rules into `/services/user-management/*`
- Introduce contracts in `/data/user-management/*`

**Phase 3 — UI Cleanup**
- Simplify `/apps` pages to orchestration + presentation only
- Move shared UI into `/components` and keep it dumb

**Phase 4 — Hardening**
- Add/standardize error handling
- Add audit logging where required
- Ensure scoping is enforced at service boundary

For each phase specify:
- Files/folders to change
- New modules to add
- Which `SUMMARY.md` files to update and what to write
- How to verify (tests, type checks, runtime behavior)

## Output Format (Required)
1. **Current State Summary** (flows, routes, where auth/scoping occurs)
2. **Target Architecture** (folders, operations, contracts, boundaries)
3. **Route → Permission Matrix**
4. **Refactor Breakdown** (file splits with names + responsibilities + LOC targets)
5. **Phased Implementation Plan** (with verification + SUMMARY.md updates)

## Constraints & Principles
- Default to **deny-by-default** permissions.
- Enforce **scoping at the service boundary** (not just UI).
- Keep modules atomic and composable.
- Update documentation (`SUMMARY.md`) as part of the change, not afterthought.

Now perform the refactor plan and provide the report.
